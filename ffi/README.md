# int2dds-ffi

C/C++ FFI (Foreign Function Interface) bindings for the int2dds DDS implementation.

## Overview

This crate provides a C-compatible API for the int2dds DDS middleware, enabling integration with:
- C/C++ applications
- Other language bindings (Python, Java, etc.)

## Architecture

```
┌─────────────────────────────────────┐
│       C/C++ Application             │
└──────────────┬──────────────────────┘
               │ C API
               ▼
┌─────────────────────────────────────┐
│        int2dds-ffi (this crate)     │
│  - C-compatible function exports    │
│  - Opaque pointer types             │
│  - Error code conversion            │
│  - Dynamic XTypes support           │
└──────────────┬──────────────────────┘
               │ Rust API
               ▼
┌─────────────────────────────────────┐
│           int2dds (core)            │
│  - DDS implementation               │
│  - RTPS protocol                    │
│  - Type system & XTypes             │
└─────────────────────────────────────┘
```

## Building

### Build the library

```bash
# Build as dynamic library
cargo build -p int2dds-ffi

# Build release version
cargo build -p int2dds-ffi --release
```

This generates:
- **Dynamic library**: `target/debug/int2dds_ffi.dll` (Windows) or `.so` (Linux) or `.dylib` (macOS)
- **Static library**: `target/debug/libint2dds_ffi.a`
- **C header file**: `ffi/include/int2dds-ffi.h` (auto-generated by cbindgen)

### Build configuration

The crate produces three library types:
- `cdylib`: Dynamic library for C/C++ linking
- `staticlib`: Static library for C/C++ linking
- `rlib`: Rust library for other Rust crates

## Header File

The C header file is automatically generated during build using [cbindgen](https://github.com/mozilla/cbindgen).

Configuration: [`cbindgen.toml`](cbindgen.toml)

The generated header includes:
- Function declarations with `extern "C"`
- Opaque struct definitions
- Error code constants
- QoS constants
- Status mask constants
- XTypes field type and member flag constants

#### Environment Configuration

These functions mutate the **process** environment and must be called before
the first `int2dds_create_participant()`. The Rust core consults
`INT2DDS_MULTICAST_TTL` only when no `int2dds.transport.UDPv4.multicast_ttl`
PropertyQosPolicy entry is set, so explicit QoS always wins.

See [docs/guide/env.md](../docs/guide/env.md) for the full environment
variable reference.

## Data Format

The FFI uses **CDR serialization** with raw bytes:
- C applications send/receive raw CDR-serialized byte arrays
- `int2dds_write_serialized()` sends CDR bytes with optional key bytes
- `int2dds_take_serialized()` / `int2dds_read_serialized()` receive CDR bytes into caller-provided buffers
- `int2dds_take_serialized_w_info()` / `int2dds_read_serialized_w_info()` additionally return `Int2DdsSampleInfo`
- `int2dds_take_serialized_batch()` takes multiple samples at once

### TypeInfo Builder (for XTypes topic creation)

```c
// Create type info with extensibility
Int2DdsTypeInfo* ti;
int2dds_type_info_create("SensorData", INT2DDS_EXTENSIBILITY_APPENDABLE, &ti);

// Add fields with type and flags
int2dds_type_info_add_field_primitive(ti, "sensor_id", INT2DDS_FIELD_INT32, INT2DDS_MEMBER_KEY);
int2dds_type_info_add_field_primitive(ti, "temperature", INT2DDS_FIELD_FLOAT64, 0);
int2dds_type_info_add_field_primitive(ti, "humidity", INT2DDS_FIELD_FLOAT64, 0);
int2dds_type_info_add_field_primitive(ti, "location", INT2DDS_FIELD_STRING, 0);

// Create topic with type info (enables XTypes discovery)
int2dds_create_topic_with_type_info(participant, "SensorTopic", ti, NULL, &topic);

int2dds_type_info_destroy(ti);
```

### Dynamic Type Discovery (XTypes Phase 1)

```c
// Wait for a publisher's TypeObject to be discovered
Int2DdsTypeObject* type_obj;
char type_name[256];
int2dds_wait_for_type_object(participant, "SensorTopic", 10000, &type_obj, type_name, 256, &name_len);

// Introspect the type
uint32_t member_count;
int2dds_type_object_member_count(type_obj, &member_count);

for (uint32_t i = 0; i < member_count; i++) {
    char name[128];
    Int2DdsMemberInfo info;
    int2dds_type_object_member_name(type_obj, i, name, 128, &len);
    int2dds_type_object_member_info(type_obj, i, &info);
    // info.member_id, info.type_kind, info.flags
}

// After receiving a sample, extract fields dynamically
int32_t sensor_id;
double temperature;
char location[256];
int2dds_dynamic_get_field_int32(data, "sensor_id", &sensor_id);
int2dds_dynamic_get_field_float64(data, "temperature", &temperature);
int2dds_dynamic_get_field_string(data, "location", location, 256, &len);

int2dds_type_object_destroy(type_obj);
```

## Usage Example

```c
#include "int2dds-ffi.h"

int main() {
    Int2DdsRet ret;
    Int2DdsParticipantFactory* factory = NULL;
    Int2DdsParticipant* participant = NULL;
    Int2DdsPublisher* publisher = NULL;
    Int2DdsSubscriber* subscriber = NULL;

    // Initialize
    ret = int2dds_domain_participant_factory_get_instance(&factory);
    if (ret != INT2DDS_RET_OK) return -1;

    // Create domain participant
    ret = int2dds_create_participant(factory, NULL, 0, &participant);
    if (ret != INT2DDS_RET_OK) return -1;

    // Create publisher
    ret = int2dds_create_publisher(participant, &publisher);
    if (ret != INT2DDS_RET_OK) return -1;

    // Create subscriber
    ret = int2dds_create_subscriber(participant, &subscriber);
    if (ret != INT2DDS_RET_OK) return -1;

    // ... use publisher/subscriber ...

    // Cleanup
    int2dds_delete_publisher(publisher);
    int2dds_delete_subscriber(subscriber);
    int2dds_delete_participant(participant);
    int2dds_domain_participant_factory_finalize(factory);

    return 0;
}
```

## Thread Safety

All opaque types use `Arc` (atomic reference counting) internally and are marked as `Send + Sync`. The API is thread-safe when used correctly:
- Multiple threads can safely call functions on the same entities
- Users must ensure proper synchronization for shared state
- Follow standard DDS threading patterns

### Listener Callbacks

Listener callbacks are invoked from DDS background threads:
- Callbacks must be thread-safe
- Multiple callbacks may execute concurrently
- Callbacks should return quickly to avoid blocking DDS
- Do not delete entities inside their own callbacks
- User context pointer must remain valid until entity deletion

## Development

### Regenerate C header

The header is auto-generated during build, but you can manually regenerate:

```bash
cbindgen --config cbindgen.toml --crate int2dds-ffi --output include/int2dds-ffi.h
```

### Adding new FFI functions

1. Add Rust function with `#[no_mangle]` and `extern "C"`
2. Use opaque pointer types from `types.rs`
3. Return `Int2DdsRet` error codes
4. Document safety requirements
5. Rebuild to regenerate header

### Testing

FFI tests are included in each module:

```bash
cargo test -p int2dds-ffi
```
