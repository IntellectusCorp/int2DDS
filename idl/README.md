# int2dds-idl

OMG IDL code generator for [int2DDS](https://crates.io/crates/int2dds), a Rust
implementation of the Data Distribution Service (DDS) with RTPS protocol support.

`int2dds-idl` reads `.idl` files and emits type definitions that are ready to use with
int2DDS in Rust, C, Python, C#, and Java. It can also emit an XML type representation for
int2DDS dynamic types and DDS-RPC scaffolding for IDL `interface` definitions. Every
generated type carries its own CDR/XCDR serialization and TypeObject description, so a type
defined once in IDL can be published from one language and received in another.

The crate ships both a command-line tool (`int2dds-idl`) and a library (`int2dds_idl`) that
exposes the parser, the resolver, and the code generators.

## Features

- Rust, C, Python, C#, and Java backends from a single IDL source
- XML type representation for int2DDS dynamic types
- DDS-RPC client and service scaffolding from IDL `interface` definitions
- DDS-XTypes annotations: `@key`, `@optional`, `@extensibility`, `@id`, `@hashid`, and more
- `#include` resolution for cross-package IDL such as ROS2 message packages
- ROS2-compatible DDS type naming
- Batch generation of every language from several IDL files in one run
- Interactive wizard when started without arguments

## Installation

### From crates.io

```bash
cargo install int2dds-idl
```

Cargo places the `int2dds-idl` binary in its bin directory (`~/.cargo/bin`), which is on
`PATH` for a standard Rust installation.

### From source

```bash
git clone https://github.com/IntellectusCorp/int2DDS.git
cd int2DDS
cargo build -p int2dds-idl --release
# target/release/int2dds-idl (int2dds-idl.exe on Windows)
```

During development the generator can also be run through Cargo without installing it:

```bash
cargo run -p int2dds-idl -- <OPTIONS> <INPUT.idl>
```

### As a library

```toml
[dependencies]
int2dds-idl = "1.0.0"
```

See [Library use](#library-use) for the API.

## Quick start

Given `HelloWorld.idl`:

```idl
struct HelloWorld {
    unsigned long index;
    string message;
};
```

Generate the Rust type:

```bash
int2dds-idl HelloWorld.idl --rust hello_world.rs
```

The output is an ordinary Rust module whose struct derives `DdsType`, so it can be used as a
topic type right away:

```rust,ignore
// Auto-generated by int2dds-idl from HelloWorld.idl
// DO NOT EDIT - changes will be overwritten

use int2dds::DdsType;

#[derive(DdsType)]
pub struct HelloWorld {
    pub index: u32,
    pub message: String,
}
```

Every other target is one flag away:

```bash
int2dds-idl HelloWorld.idl --c-header hello_world.h     # C header
int2dds-idl HelloWorld.idl --python hello_world.py      # Python module
int2dds-idl HelloWorld.idl --csharp HelloWorld.cs       # C# source
int2dds-idl HelloWorld.idl --java generated/java        # Java (a directory, one file per type)
int2dds-idl HelloWorld.idl --xml hello_world.xml        # XML type representation
int2dds-idl HelloWorld.idl --rpc hello_world_rpc.rs     # Rust types plus DDS-RPC scaffolding
```

Or generate every target at once into a directory:

```bash
int2dds-idl HelloWorld.idl --output-dir generated
```

Running `int2dds-idl` with no arguments starts an [interactive wizard](#interactive-wizard)
that asks the same questions step by step.

## Choosing what gets generated

The generator decides its outputs from three sources, in this order of precedence:

1. **A language flag with a path** (`--rust`, `--c-header`, `--python`, `--csharp`, `--xml`,
   `--rpc`, or `--java <DIR>`) generates exactly that target at exactly that path.
2. **`--output-dir <DIR>`** generates every target that has no explicit flag, naming each file
   after the IDL file.
3. **Neither** falls back to writing `<name>.rs` and `<name>.h` into the current directory.

Both forms combine: `--output-dir generated --rust src/types.rs` writes the Rust module to
`src/types.rs` and everything else under `generated/`.

Auto-named files derive from the IDL file name converted to `snake_case`
(`HelloWorld.idl` becomes `hello_world`); the C# file uses `PascalCase` instead, and Java
names each file after the type it contains:

| Target | Auto-named output for `HelloWorld.idl` |
|--------|----------------------------------------|
| Rust   | `hello_world.rs`                       |
| C      | `hello_world.h`                        |
| Python | `hello_world.py`                       |
| C#     | `HelloWorld.cs`                        |
| Java   | `HelloWorld.java` (one file per type, under the package path if `--java-package` is set) |
| XML    | `hello_world.xml`                      |
| RPC    | `hello_world_rpc.rs`                   |

Several IDL files can be passed in one invocation. Each is processed independently, so with
`--output-dir` every file gets its own set of outputs. An explicit path flag, on the other
hand, names a single file, so passing several inputs with `--rust types.rs` overwrites
`types.rs` with each input in turn; use `--output-dir` for multi-file runs.

Missing parent directories are created automatically. Each written file is reported on
stderr as `generated: <path>`, and any parse, resolve, or write error stops the run with
exit code 1.

## Interactive wizard

Start `int2dds-idl` without arguments to be guided through the same choices interactively:

1. **IDL files.** The wizard scans the current directory (four levels deep, skipping
   `target/`, `.git/`, `node_modules/`, and `.cargo/`) and offers every `.idl` file it finds
   as a checklist. Paths can also be typed by hand, with Tab completion.
2. **Languages.** A checklist of Rust, C, Python, C#, XML, RPC, and Java. Rust is
   pre-selected.
3. **Output directory.** Defaults to `generated`.
4. **Advanced options** (optional). ROS2 type naming with its package and interface kind,
   and `#include` search paths are always asked; the Rust crate path, the Python module
   path, the C# namespace, the Java package, and the C string mode and default size are
   asked only for the selected languages.

The wizard always generates into the output directory with auto-named files, exactly like
`--output-dir` restricted to the selected languages.

```
                              file per type)
    -x, --xml <PATH>          Generate XML type representation to PATH
    -o, --output-dir <DIR>    Output directory (auto-names files)
    -I, --include <DIR>       Add a search directory for #include resolution (repeatable)
    --crate-path <PATH>       Rust crate path (default: int2dds)
    --python-module <PATH>    Python module path (default: int2dds)
    --csharp-namespace <NS>   C# namespace (default: GeneratedTypes)
    --java-package <PKG>      Java package (default: none -- unnamed package,

                              flat IDL infers the package from a <package>/msg/File.idl path
    --ros2-package <NAME>     Override the package for flat (module-less) IDL under --ros2
    --ros2-kind <KIND>        Interface kind (msg|srv|action) for --ros2-package (default: msg)
    -h, --help                Print help
    -V, --version             Print version
```

### Output targets

| Option | Output |
|--------|--------|
| `-r, --rust <PATH>` | One Rust module with `#[derive(DdsType)]` structs, enums, bitmasks, bitsets, unions, and constants. |
| `-c, --c-header <PATH>` | One C header with struct definitions and `static inline` CDR serialization helpers built on `int2dds_cdr.h`. |
| `-p, --python <PATH>` | One Python module of dataclasses with CDR serialization methods for the int2DDS Python binding. |
| `-s, --csharp <PATH>` | One C# source file of `IDdsType` classes for the int2DDS C# binding. |
| `-j, --java <DIR>` | One `.java` file per top-level type for the int2DDS Java binding. This is the only target that takes a directory. |
| `-x, --xml <PATH>` | The XML type representation loaded by `int2dds::config::xml::XmlTypeRegistry`. |
| `--rpc <PATH>` | A Rust module with the IDL types and, for every `interface`, the request/reply types, a service trait, a client, and a service wrapper for `int2dds-rpc`. |
| `-o, --output-dir <DIR>` | Every target above that has no explicit flag, auto-named under `DIR`. |

The target flags may be combined freely in one invocation:

```bash
int2dds-idl Strings.idl \
  --rust   generated/strings.rs \
  --python generated/strings.py \
  --csharp generated/Strings.cs \
  --java   generated/java \
  --crate-path my_dds \
  --csharp-namespace MyApp.Types \
  --java-package myapp.types
```

### `-I, --include <DIR>`

Adds a directory to search when resolving `#include` directives. It may be repeated. Each
include is first tried relative to the directory of the file that contains it, then against
every `-I` directory in the order given. See [Includes](#includes-include) for what the
included files contribute.

### `--crate-path <PATH>`

The Rust path under which int2DDS is available to the generated code (default `int2dds`).
The Rust and RPC backends import `DdsType` from this path and record it in the derive
attribute, and the RPC backend derives the DDS-RPC crate name from it by appending `_rpc`:

```rust,ignore
use my_dds::DdsType;
use my_dds_rpc::client::{Client, ClientParams};

#[derive(DdsType)]
#[dds_type(crate_path = "my_dds")]
pub struct HelloWorld { /* ... */ }
```

Use it when the dependency is renamed in `Cargo.toml` or re-exported from another crate.

### `--python-module <PATH>`

The module path the generated Python code imports the CDR support from (default `int2dds`).
The output imports `CdrReader`, `CdrWriter`, `Extensibility`, and `Float128` from
`<PATH>.cdr`, so point this at the package that provides the int2DDS Python binding if it is
vendored under another name.

### `--csharp-namespace <NS>`

The namespace that wraps all generated C# classes (default `GeneratedTypes`). Dotted names
such as `MyApp.Types` are accepted as is.

### `--java-package <PKG>`

The Java package declared by every generated class. With `--java-package com.example` the
files land under `<DIR>/com/example/` and start with `package com.example;`. Without it the
classes belong to the unnamed package and land flat in `DIR`. An invalid package name is
rejected before any file is written.

### `--string-bound <N>` and `--string-pointer`

These two options control how the C backend represents strings.

By default an IDL `string` becomes a fixed-size `char` array sized to hold the bound plus a
terminating NUL. A bounded `string<256>` becomes `char field[257]`; an unbounded `string`
uses `--string-bound` as its bound, so the default of 256 also yields `char field[257]`, and
`--string-bound 64` yields `char field[65]`. Unbounded `wstring` members are sized the same
way as `uint16_t` arrays.

With `--string-pointer`, `string` members become `char*` pointers that the deserializer
allocates with `malloc`, which matches the OMG IDL-to-C mapping. The header then includes
`<stdlib.h>` and emits a `<Type>_init` helper that zeroes a struct and, for structs that own
heap members, a `<Type>_cleanup` helper that frees them. `wstring` members stay fixed arrays
in both modes.

### `--rpc <PATH>`

Generates a Rust module containing the IDL types followed by DDS-RPC scaffolding for each
`interface`. See [RPC](#rpc) below for the generated items and the `int2dds-rpc` crate they
plug into. When `--output-dir` is used without `--rpc`, the RPC module is still produced as
`<name>_rpc.rs`; for an IDL file without interfaces it contains only the types.

### `--ros2`, `--ros2-package <NAME>`, and `--ros2-kind <KIND>`

Rewrite the registered DDS type name to the convention ROS2 uses over DDS. See
[ROS2-compatible naming](#ros2-compatible-naming---ros2). `--ros2-kind` accepts `msg`, `srv`,
or `action` and is validated up front.

### `-h, --help` and `-V, --version`

Print the usage text or `int2dds-idl <version>` and exit.

## Using the generated code

### Rust

The Rust backend emits plain structs with `#[derive(DdsType)]`, so a generated module needs
the same dependencies as a hand-written int2DDS type:

```toml
[dependencies]
int2dds = "1.0.0"
speedy = "0.8"
log = "0.4"
```

Include the module in your crate and hand the type to a `DataWriter` or `DataReader` like
any other `DdsType`:

```rust,ignore
mod hello_world; // generated with --rust src/hello_world.rs
use hello_world::HelloWorld;

let topic = participant
    .create_topic::<HelloWorld>("HelloWorldTopic", "HelloWorld", TopicQos::default(), None, StatusMask::default())
    .unwrap();
```

IDL `module`s do not become Rust modules; every type lands at the top level of the generated
file, and the module scope is kept in the registered DDS type name. Identifiers that collide
with Rust keywords are escaped (`type` becomes `r#type`).

### C

The C header contains the struct definitions and, for every struct, `static inline`
serialization helpers:

| Helper | Purpose |
|--------|---------|
| `<Type>_serialize_cdr(val, buf, capacity, xcdr2)` | Serialize into `buf` with the XCDR1 or XCDR2 encapsulation; returns the byte count, or 0 on error. |
| `<Type>_serialize_for(writer, val, buf, capacity)` | Same, choosing the representation from the `DataWriter`'s QoS. |
| `<Type>_deserialize_cdr(buf, len, out)` | Parse a received sample; returns `false` on malformed data. |
| `<Type>_type_info()` | The type description registered when the topic is created. |
| `<Type>_create_topic(participant, topic_name, qos, topic_out)` | Create a topic for the type, registering `<Type>_type_info()` with it. |
| `<Type>_init` / `<Type>_cleanup` | Only with `--string-pointer`: zero the struct, and free its heap members (`_cleanup` exists only for structs that have any). |

The helpers are built on `int2dds_cdr.h`, the CDR utility library shipped under
`ffi/include/` in the int2DDS repository, which the generated header includes itself.
`<Type>_serialize_for` and `<Type>_create_topic` use handles from `int2dds-ffi.h`, so include
that one before the generated header. The CDR library can be used header-only by defining
`INT2DDS_CDR_STATIC` before the generated header, or compiled once from
`ffi/src/cdr_utils.c` and linked:

```c
#include "int2dds-ffi.h"
#define INT2DDS_CDR_STATIC
#include "hello_world.h"
```

See the [FFI guide](https://github.com/IntellectusCorp/int2DDS/blob/main/ffi/README.md) for
building a C application against int2DDS.

### Python

The Python backend emits dataclasses that serialize themselves through the `int2dds.cdr`
module of the int2DDS Python binding. A generated class is passed directly to
`create_topic`:

```python
from int2dds import DomainParticipant
from hello_world import HelloWorld  # generated with --python hello_world.py

with DomainParticipant(domain_id=0) as dp:
    topic = dp.create_topic("HelloWorldTopic", HelloWorld)
    writer = dp.create_publisher().create_datawriter(topic)
    writer.write(HelloWorld(index=1, message="hello"))
```

Enums become `IntEnum`, bitmasks become `IntFlag`, and keyword collisions take a trailing
underscore (`class` becomes `class_`). See the
[Python guide](https://github.com/IntellectusCorp/int2DDS/blob/main/python/README.md).

### C#

The C# backend emits classes implementing `Int2Dds.Types.IDdsType` inside the namespace
given by `--csharp-namespace`. They require the `Int2Dds` assembly of the int2DDS C#
binding and are used as the type argument of the binding's topic and writer/reader APIs.
Member names are converted to `PascalCase`, and keyword collisions are escaped with `@`.

### Java

The Java backend emits one class per top-level type, each implementing
`kr.co.intellectus.int2dds.types.IDdsType`, which is what `DomainParticipant.createTopic`
takes:

```java
// generated HelloWorld.java
public final class HelloWorld implements IDdsType {

    public int index;
    public String message = "";

    @Override public String typeName() { return "HelloWorld"; }
    @Override public Extensibility extensibility() { return Extensibility.APPENDABLE; }
    @Override public void serializeCdr(CdrWriter writer) { /* ... */ }
    @Override public void deserializeCdr(CdrReader reader) { /* ... */ }
}
```

Fields are public, and unsigned IDL integers map to the Java signed type of the **same
width** (`unsigned long` becomes `int`), wrapping rather than widening. Sequences and arrays
both map to Java arrays rather than `List<T>`, so no element is boxed.

Every struct also overrides `typeInfo()`, describing all of its members (kinds, bounds,
`@key` flags, nested structs and enums) so `createTopic` advertises the same TypeObject the
other backends do; a generated enum exposes its own description as a static `typeInfo()`.
A keyed struct that cannot be fully described is refused rather than emitted as a key-less
type.

Java requires one public top-level class per file, so `-j` takes a directory and a single
`.idl` declaring several types produces several `.java` files. Two IDL types that map to the
same class name (`foo_bar` and `FooBar`) are refused instead of silently overwriting each
other, and when several inputs in one run write the same path the second one reports the
overwrite.

The backend refuses, with an error naming the declaration, constructs it cannot yet encode
correctly rather than emit Java that compiles and writes the wrong bytes:

| Construct | Why |
|---|---|
| `union`, `bitmask`, `bitset` | no Java mapping implemented yet |
| `map<K, V>` | no Java mapping implemented yet |
| `@optional` members | the optional member framing (XCDR1 parameter header, XCDR2 presence flag, or EMHEADER under MUTABLE) is not emitted yet |
| `@extensibility(MUTABLE)` structs | same, the EMHEADER framing is not emitted yet |
| struct inheritance | no Java mapping implemented yet |
| `enum` with no variants | an empty Java `enum` body is not valid Java |
| nested collections (`sequence<sequence<T>>`, `long m[3][4]`) | Java array creation needs the sized dimension first, and no test exercises a nested encoding against real CDR bytes |
| cross-package type references | see the [reference contract](#includes-include) |
| a keyed struct whose nested-struct members form a cycle (e.g. an `@external` self-reference) | the cyclic member has no TypeObject form here, and without a full description the topic would be created key-less |

With an explicit `-j` (or Java selected in the wizard) a refusal fails the run. In a plain
`--output-dir` batch, where Java is only implied, the refusal is reported as a warning, Java
is skipped for that file, and the other languages are still generated. See the
[Java guide](https://github.com/IntellectusCorp/int2DDS/blob/main/java/README.md) for the
binding-side workflow.

### XML

The XML backend emits the type representation that int2DDS loads at runtime for dynamic
types, mirroring the resolved model one to one so that the XML path produces the same
TypeObject as the generated Rust type:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!-- Auto-generated by int2dds-idl from Strings.idl -->
<dds>
  <types>
    <struct name="StringsType">
      <member name="id" type="int32" key="true"/>
      <member name="unbounded_str" type="string"/>
      <member name="bounded_str" type="string" stringMaxLength="256"/>
    </struct>
  </types>
</dds>
```

Load it with `int2dds::config::xml::XmlTypeRegistry` (`load_file` or `load_str`) and look
the type up by name to obtain a `DynamicTypeSupport`, which lets an application publish or
subscribe to a type it did not compile in.

### RPC

`--rpc` turns every IDL `interface` into DDS-RPC scaffolding for the
[int2dds-rpc](https://crates.io/crates/int2dds-rpc) crate. The generated module starts with
the regular IDL types and then, for an interface `RobotControl`, adds:

| Generated item | Description |
|---|---|
| `RobotControl` trait | The service interface to implement, one method per IDL operation. Operations that `raises` an exception return `Result`. |
| `RobotControlClient` | A type-safe client with a method per operation. |
| `RobotControlService` | Wraps your `RobotControl` implementation so a `Server` can dispatch requests to it. |
| `RobotControl_<op>_In` / `_Out` / `_Result` | Per-operation request, reply, and result types mapped as the DDS-RPC specification prescribes. |
| `RobotControl_Request` / `RobotControl_Reply` | The request and reply topic types, with the operation and exception hash constants. |

IDL `exception`s become `DdsType` structs. Add `int2dds-rpc` next to `int2dds` in
`Cargo.toml`; the generated imports follow `--crate-path`, so a renamed `my_dds` dependency
expects its RPC crate as `my_dds_rpc`. The
[int2dds-rpc README](https://github.com/IntellectusCorp/int2DDS/blob/main/rpc/README.md)
walks through implementing the service and calling it from a client.

## Supported IDL

The parser and resolver cover the IDL constructs int2DDS uses on the wire:

| Construct        | Example                                               |
|------------------|-------------------------------------------------------|
| Primitives       | `boolean octet char/wchar short/long/long long (+ unsigned) float double` |
| Strings          | `string`, `string<256>`, `wstring`, `wstring<N>`      |
| Sequences        | `sequence<long>`, `sequence<long, 10>` (bounded)      |
| Arrays           | `long values[16]`                                     |
| Maps             | `map<long, string>`                                   |
| Structs          | nested structs, struct inheritance (`@key` members)   |
| Enums            | `enum Color { RED, GREEN, BLUE };`                    |
| Unions           | `union U switch(long) { case 0: long a; default: ...}`|
| Bitmask / Bitset | `@bit_bound(8) bitmask`, `bitset { bitfield<3> a; }`  |
| Modules          | `module pkg { module msg { struct T {...}; }; };`     |
| Typedefs         | `typedef sequence<long> LongSeq;`                     |
| Constants        | `const uint8 STATUS_FIX = 0;` (literal values; emitted per target) |
| Interfaces       | `interface Svc { long add(in long a, in long b) raises (Overflow); };` (RPC target) |
| Includes         | `#include "pkg/msg/Type.idl"` (resolved via `-I <dir>`; resolve-only) |

### Annotations

| Annotation               | Meaning                                               |
|--------------------------|-------------------------------------------------------|
| `@key`                   | Marks a key member                                    |
| `@extensibility(FINAL\|APPENDABLE\|MUTABLE)` | Type extensibility (default: APPENDABLE); `@final`, `@appendable`, `@mutable` are accepted as shorthand |
| `@id(N)`                 | Explicit member id                                    |
| `@autoid(HASH\|SEQUENTIAL)` | Struct-level member id policy; a bare `@autoid` means `HASH` |
| `@hashid` / `@hashid("name")` | MD5-based 28-bit member id from the member name or the given name |
| `@optional`              | Optional member                                       |
| `@must_understand`       | Member a reader must understand (MUTABLE types)       |
| `@external`              | Member stored behind an indirection (`Box` in Rust)   |
| `@default(value)`        | Default value of a member                             |
| `@value(N)`              | Explicit enum variant value                           |
| `@bit_bound(N)`          | Bitmask bit bound                                     |
| `@position(N)`           | Bitmask flag position                                 |
| `bitfield<N>`            | Bitset field width                                    |

Example with annotations:

```idl
@extensibility(APPENDABLE)
struct StringsType {
    @key long id;
    string unbounded_str;
    string<256> bounded_str;
};
```

### Includes (`#include`)

`#include "pkg/msg/Type.idl"` directives are resolved relative to the including file first,
then against each `-I <dir>` in order, and the referenced files are loaded so cross-package
type references resolve. They are **resolve-only**: included types and constants populate the
symbol table but are **not** emitted into the current file's output. Only the types and
constants declared in the input file itself are generated, so each file's output stays
self-contained and free of duplicate or leaf-name-colliding definitions
(`pkg_a::msg::Status` vs `pkg_b::msg::Status`). Generate each package's own types from its
own `.idl`.

**Reference contract.** A member whose type comes from an included file is emitted as a
reference to that type in the *dependency's* package, not a re-definition:

- **Rust:** the field uses the full package path, e.g. `pub header: std_msgs::msg::Header,`.
  The output compiles as is provided the consuming build exposes each dependency package at
  that path (one module or crate per package, types at `<pkg>::<kind>::<Type>`).
  Serialization of the nested type travels with its own `#[derive(DdsType)]`, so no extra
  `use` is needed.
- **Python:** a referenced type is imported with `from <module> import <Type>`, where
  `<module>` is the auto-named output of the included file.
- **C / C#:** emit the bare leaf name for external references; the consuming build must
  bring the dependency type (and, for C, its serialization helpers) into scope.
- **Java:** a reference is emitted as the bare leaf name, which resolves only when the
  referenced type lands in the *same* Java package. A reference that would cross packages is
  **refused** rather than emitted. In practice an included type used from the same `module`
  works; one used across modules does not. Generate each file separately into the same
  output directory and the packages line up.

This contract is the integration point for per-package generators such as the ROS2 `rmw`
layer, which generates each package separately and wires them together.

An include that cannot be found is reported as a warning and skipped. If a type from that
file is actually referenced, resolution then fails with an `unresolved type` error.

## ROS2-compatible naming (`--ros2`)

`--ros2` rewrites the **registered DDS type name** to the convention ROS2 uses over DDS,
`scope::dds_::Name_`, so int2DDS types interoperate with ROS2 nodes. Only the registered
TypeObject name changes; struct fields and serialization are untouched. In Rust the name
appears as a derive attribute:

```rust,ignore
#[derive(DdsType)]
#[dds_type(type_name = "my_pkg::msg::dds_::HelloWorld_")]
pub struct HelloWorld { /* ... */ }
```

The scope comes from the IDL modules when there are any, and from the file path or the
command line for flat IDL:

```bash
# Module-based IDL: scope comes from the modules
#   module robot_msgs { module msg { struct Pose {...}; }; };
int2dds-idl Pose.idl --rust pose.rs --ros2
#   -> robot_msgs::msg::dds_::Pose_

# Flat IDL in a ROS2-standard layout: package inferred from the path
int2dds-idl my_pkg/msg/HelloWorld.idl --rust hello.rs --ros2
#   -> my_pkg::msg::dds_::HelloWorld_

# Flat IDL elsewhere: supply the package explicitly
int2dds-idl HelloWorld.idl --rust hello.rs --ros2 --ros2-package my_pkg
#   -> my_pkg::msg::dds_::HelloWorld_

# Service or action interfaces
int2dds-idl AddTwo.idl --rust add_two.rs --ros2 --ros2-package my_pkg --ros2-kind srv
#   -> my_pkg::srv::dds_::AddTwo_
```

Flat IDL with neither a standard path nor `--ros2-package` is generated with a warning and
its names left unmangled.

For actual ROS2 to DDS communication, also align at runtime: ROS2 prefixes topics with
`rt/`, defaults to the XCDR1 data representation, and uses its standard QoS profiles.

> **Note (nested types):** flat ROS2 messages match fully. For nested messages (a struct
> referencing another ROS2-mangled type), only the top-level type's own name is mangled; the
> nested member reference in the TypeObject still uses the plain identifier, so strict XTypes
> TypeObject-hash matching of nested types is not yet covered.

## Library use

The same pipeline the CLI runs is available as a library. Parsing yields an AST, resolving
turns it into the `IdlModel` intermediate representation shared by every backend, and each
backend renders that model:

```rust,ignore
use int2dds_idl::{codegen, parser, resolver};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let source = std::fs::read_to_string("HelloWorld.idl")?;
    let defs = parser::parse_idl(&source).map_err(|e| e.to_string())?;
    let model = resolver::resolve(defs).map_err(|e| e.to_string())?;

    let opts = codegen::rust::RustOptions { crate_path: "int2dds".into() };
    let code = codegen::rust::generate(&model, "HelloWorld.idl", &opts);
    std::fs::write("hello_world.rs", code)?;
    Ok(())
}
```

The backends live in `codegen::{rust, c, python, csharp, java, xml, rpc}`, each with its own
options struct mirroring the CLI flags (`RustOptions`, `COptions`, `PythonOptions`,
`CSharpOptions`, `JavaOptions`). The Java backend returns one `GeneratedFile` per type, and
the XML backend returns a `Result` because some constructs have no XML form.

To reproduce the CLI's `#include` handling, load the translation unit with
`preprocess::load_with_includes` and resolve with `resolver::resolve_scoped`, which keeps
included definitions for reference resolution but emits only the root file's own types:

```rust,ignore
use int2dds_idl::{parser, preprocess, resolver};
use std::path::{Path, PathBuf};

let root = Path::new("sensor_msgs/msg/Imu.idl");
let include_dirs = vec![PathBuf::from("ros2_idl")];
let (unit, missing) = preprocess::load_with_includes(root, &include_dirs)?;
let all = parser::parse_idl(&unit).map_err(|e| e.to_string())?;
let own = parser::parse_idl(&std::fs::read_to_string(root)?).map_err(|e| e.to_string())?;
let model = resolver::resolve_scoped(&own, all).map_err(|e| e.to_string())?;
```

`naming` exposes the case conversions and keyword escaping the backends share, including the
ROS2 mangling helpers.
